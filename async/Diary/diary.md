Approach to solving the Async task, which required sending 3,000 data items to a server while strictly managing a 20-request concurrency limit, handling 500/503 errors, and enforcing a strict 60-second execution timeout. As a student continuing to learn advanced TypeScript and asynchronous JavaScript, this was a great exercise in orchestrating Promises.
My first thought was to use Promise.all(), but I quickly realized that throwing 3,000 requests at the server at once would immediately trigger the 503 Server Overload limits.
A recursive queue/pool function: Creating a function that fires up to 20 workers, and whenever one finishes, it pulls the next item from the array. Building my own while-loop based promise pool inside the task function because implementing the logic from scratch is the best way to understand. 
Concurrency Control: I tracked activeRequests and used a while loop to push new requests as long as activeRequests < 20. A .finally() block on the Promise ensures that whenever a request finishes (success or fail), activeRequests decrements and the next item is processed.
Retry Logic: I wrapped the fetch call in a while (attempts < 3) loop. If the server returned a 500 error, it would simply loop again. If it hit 200 or 503, it would return out of the loop and record the specific state.
I noticed the severe penalty for using console.log. I had to make sure I relied exclusively on console.info, console.error, and console.warn to track the lifecycle of the items and print the final summary.
Hurdle:
Because of the server's concurrency limit (only 20 at a time) and the built-in delay (100ms–1100ms per request), the system physically cannot process all 3,000 items in 60 seconds. A 20-request concurrency limit × ~600ms average delay equals a maximum throughput of ~2,000 items. The task is mathematically impossible to finish! This "Aha!" moment changed my approach. Instead of optimizing for speed, I focused on resilience—ensuring that when the AbortSignal triggers, active requests finish gracefully, the queue halts, and the untouched items are accurately tallied as Skipped.

Note: server.ts and tsconfig.json were left completely untouched as they are the provided boilerplate environment. All concurrency, retry, and timeout logic was implemented strictly inside index.ts and executor.ts.
